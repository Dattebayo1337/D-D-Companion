# Лобби игроков и мастера

## Что доступно

- Пользователь входит в личный аккаунт и создаёт лобби в разделе «Общее лобби». Создатель становится мастером именно этого лобби. Регистрация и перенос прежних данных описаны в [ACCOUNTS.md](ACCOUNTS.md).
- Мастер выбирает кампанию и персонажей, чьи полные листы будут видны группе. Заметки **персонажа** входят в опубликованный лист.
- Игрок открывает ссылку `/play#invite=…`, вводит имя и получает роль «Игрок». Роль не выбирается в форме и не принимается сервером от клиента.
- Все участники видят полные листы выбранных героев: характеристики, навыки, ресурсы, инвентарь, заклинания, справочные описания, заметки. Листы доступны для просмотра; редактирование остаётся в личном пространстве мастера.
- Кампания, её NPC, задания, локации, записи сессий и отдельные заметки лобби доступны только мастеру. Они не включаются в ответ API игроку.
- Изменения перечитываются каждые 5 секунд. При потере доступа листы убираются из интерфейса; уже прочитанные или скопированные сведения отозвать невозможно.
- Можно заменить приглашение, закрыть лобби, снова открыть его или исключить участника. Исключение также отключает старую ссылку. Замена ссылки не завершает уже выданные сессии других игроков.

## Первый вход на этом компьютере

Создайте аккаунт владельца по инструкции [ACCOUNTS.md](ACCOUNTS.md): вкладка «Регистрация», однократный ключ из `.local/host-key.txt` либо `DND_HOST_KEY`. После переноса прежних данных вход выполняется по логину и паролю. Не передавайте установочный ключ игрокам.

`DND_HOST_KEY` используется только для первоначальной настройки владельцем. Сессии аккаунтов и игроков действуют 7 дней и хранятся в HttpOnly cookies. Игрок может войти по приглашению с аккаунтом или как гость.

Главная страница, справочники, поиск, источники и чтение API каталогов доступны без ключа и токена. Личный аккаунт нужен для создания лобби и доступа к собственным данным; управление конкретным лобби доступно его владельцу. Изменения базы и API персонажей, кампаний и заметок защищены проверками аккаунта и владельца; внутри API лобби права проверяются повторно. История импортов доступна администратору установки.

## Размещение в интернете

Подготовлен вариант для **одного VPS с постоянным диском**, Docker Compose и доменом. Публичный сервер в рамках разработки не создавался. Docker-конфигурация требует проверки на выбранном Linux-сервере; локально проверены приложение, миграция SQLite и серверные права.

1. На выбранном VPS установите Docker Engine с Compose по официальной инструкции поставщика. Домен направьте A-записью на IP сервера; при наличии AAAA она также должна вести на этот сервер. Разрешите входящие TCP 80 и 443. Порт приложения 3000 наружу не публикуется.
2. Скопируйте исходники проекта на сервер. Не переносите `.local`, `node_modules`, `.next` и локальный `.env`.
3. В каталоге проекта создайте `deployment.env`:

   ```sh
   umask 077
   printf 'SITE_DOMAIN=dnd.example.com\nDND_HOST_KEY=%s\n' "$(openssl rand -hex 32)" > deployment.env
   ```

   Замените `dnd.example.com` своим доменом. Сохраните сгенерированный ключ в менеджере паролей.
4. Запустите:

   ```sh
   docker compose --env-file deployment.env up -d --build
   docker compose --env-file deployment.env logs --tail=100 app caddy
   ```

   При запуске применяются добавочные миграции. Caddy получает HTTPS-сертификат для домена. `APP_ORIGIN` фиксирует разрешённый внешний origin и включает Secure cookies за обратным прокси.
5. Для новой пустой базы загрузите подготовленные справочники:

   ```sh
   docker compose --env-file deployment.env exec app node --import ./scripts/register.mjs scripts/import-srd.ts
   ```

6. Откройте `https://ваш-домен/login`, создайте аккаунт владельца с однократным установочным ключом, создайте персонажей и кампанию, затем лобби. Получите приглашение, находясь именно на публичном домене. Ссылка на `localhost` не работает у других игроков.
7. Проверьте приглашение в приватном окне браузера: гость видит листы, но `/api/campaigns`, `/api/characters` ему недоступны, а главная страница и справочники открываются без входа. Проверьте отзыв доступа и закрытие лобби.

Инструкции инфраструктуры: https://docs.docker.com/engine/install/ и https://caddyserver.com/docs/automatic-https

## Данные, перенос и резервные копии

SQLite хранится в именованном томе `companion-data` и переживает пересоздание контейнера. **Не выполняйте `docker compose down -v`**, если хотите сохранить данные. Ключ мастера из `deployment.env` также нужен после обновления. Не запускайте несколько реплик с независимыми SQLite-базами.

Чтобы перенести текущую локальную базу, остановите локальное приложение и сделайте копию `prisma/companion.db`. На сервере сначала остановите приложение и поместите копию в том как `/data/companion.db`, затем запустите приложение для применения миграций. Не копируйте открытую SQLite-базу обычным копированием во время записи.

Для резервной копии серверной базы:

```sh
mkdir -p backups
docker compose --env-file deployment.env stop app
docker compose --env-file deployment.env cp app:/data/companion.db ./backups/companion.db
docker compose --env-file deployment.env start app
```

Храните копии отдельно от VPS, поскольку они содержат персонажей, кампании и заметки. Для обновления исходников: сделайте копию, обновите файлы и повторите `up -d --build`. Данные и ключ не включаются в архив исходников. Для PostgreSQL добавлена соответствующая миграция лобби; приведённый Compose использует SQLite.

## Границы текущей реализации

Независимые аккаунты и лобби поддерживаются. Редактирование опубликованного листа другим игроком, чат и видеосвязь в эту версию не входят. Пользователь с приглашением видит все опубликованные листы выбранного лобби. Имя гостя само по себе не подтверждает его личность.
