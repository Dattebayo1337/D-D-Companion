# Резервные копии и перенос

Резервирование состоит из двух частей: SQLite на сервере и локальные данные каждого браузера. Для команд ниже нужен Node.js 24; запускайте их из папки проекта. Это инструменты администратора сервера, а не доступ игроков к чужим данным.

## База сервера

Создание согласованной копии допускается при работающем сервере через SQLite Backup API:

```powershell
node scripts/server-backup.mjs backup prisma/companion.db backups/my-session.db
node scripts/server-backup.mjs inspect backups/my-session.db
```

Папка назначения должна существовать. Выбирайте новое имя: существующая копия никогда не перезаписывается. Проверяются целостность SQLite, внешние ключи и основные таблицы приложения. Копия включает справочники, аккаунты, персонажей, кампании, лобби, подборки, личных монстров, карты и PNG, хранящиеся в базе. Пользовательские файлы вне базы, код приложения и настройки окружения в неё не входят. Храните отдельно соответствующую версию приложения и конфигурацию размещения.

Копия содержит личные заметки, секреты кампаний, хеши паролей и состояние сессий входа. Храните её в закрытом месте вне публичной папки сайта; перенесите второй экземпляр на другое устройство или защищённое хранилище. Это не файл для раздачи игрокам.

## Восстановление

1. Остановите все процессы приложения и другие подключения к этой базе. Флаг ниже подтверждает действие оператора, сам процессы не останавливает.
2. Проверьте путь к рабочей базе и копии. Восстановление заменяет **все данные**, а не объединяет кампании. Изменения после снимка исчезнут; учётные записи и действовавшие сессии также вернутся к состоянию снимка.
3. Выполните:

```powershell
node scripts/server-backup.mjs restore backups/my-session.db prisma/companion.db --server-stopped
```

Перед заменой создаётся файл `companion.db.before-restore-<UUID>.db` с текущим состоянием. Его путь выводится командой. При ошибке записи инструмент пытается вернуть эту копию. Не запускайте сервер после ошибки, пока не проверите базу командой `inspect` и сообщение об ошибке.

Входящая и рабочая базы должны иметь одинаковую схему. При переносе сначала разверните соответствующую версию приложения и её миграции. Несовместимые схемы и оставшиеся журналы SQLite блокируют восстановление. Не удаляйте журналы вручную: штатно завершите подключения. При необходимости вернуться назад используйте предварительную копию той же командой восстановления с остановленным сервером.

Инструмент предназначен только для SQLite. Для размещения с PostgreSQL используйте резервирование базы у провайдера и проверенный им процесс восстановления; этот скрипт PostgreSQL не обслуживает.

## Данные браузера

В разделе «Настройки» есть «Копия данных браузера». Она сохраняет настройки, выбранную редакцию, избранное, историю чтения и бросков, локальные черновики инструментов и кампаний. Куки входа и посторонние ключи хранилища не экспортируются.

Перед восстановлением скачайте текущую копию. Выберите JSON и подтвердите замену: меняются только одноимённые записи, остальные остаются. После успеха перезагрузите приложение предложенной кнопкой. Черновики не отправляются на сервер автоматически; сохранение кампании по-прежнему проверяет её версию и владельца. При нехватке места инструмент пытается откатить запись и явно сообщает, если откат тоже не удался.

Лимит файла — 6 МБ. Формат контейнера, допустимые ключи и JSON проверяются при загрузке; схемы конкретных черновиков дополнительно проверяют соответствующие экраны. Файл может включать секретные черновики мастера, поэтому его тоже следует хранить приватно. Такая копия не заменяет базу сервера и не переносит вход в аккаунт.

Автономные снимки публичных справочников в IndexedDB не входят в JSON-копию настроек. Для их переноса сохраните выбранные карточки заново на нужном устройстве. Журнал, казна и материалы лобби входят в полную копию базы сервера.
